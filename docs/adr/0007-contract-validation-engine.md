# 7. Contract validation reproduces Zod semantics

Date: 2026-09-30
Status: accepted

## Context

The reference contract is a Zod 3 schema. Consumers compare diagnostics by `path`, `code` and `params.reason`, and a front end may validate the same document with the TypeScript package. Pydantic reports errors with different shapes, union handling and ordering, so matching the reference through Pydantic would need an adapter full of special cases.

## Decision

- `survey_structure/_schema.py` implements the small set of Zod combinators the contract uses (object, strict keys, union, discriminated union, record, array, lazy, optional, nullable, refine) with Zod's evaluation rules: valid, dirty and aborted states, the first dirty union branch winning, refinements running on dirty values, and default English messages.
- `survey_structure/schemas.py` declares the contract in the same order as the TypeScript source, because key order decides issue order.
- `_js.py` reproduces the JavaScript semantics the rules rely on: `typeof`, `===`, property order with array indices first, UTF-16 string length, `String()` and the ECMAScript whitespace class.
- Parsed documents are plain dictionaries. `survey_structure/types.py` provides `TypedDict` definitions for static checking. Pydantic is not used by the base package.
- Parity is verified against 217 reference cases, 73 language tags and 1,012 pattern and value combinations generated by the reference implementation.

## Consequences

- Issues are identical to the reference, including messages, so API errors can be compared or forwarded unchanged.
- Changes to the TypeScript contract are ported rule by rule; the goldens point to any behavior not yet ported.
- Localized messages (`localizeSurveyValidationIssue`) are ported in `survey_structure.diagnostics` and checked for every reference case in both languages.
